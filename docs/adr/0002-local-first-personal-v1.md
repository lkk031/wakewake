# ADR 0002：个人日用 V1 采用本地优先单用户架构

- 状态：已采纳
- 日期：2026-07-26

## 背景

原构建基线把账号、跨设备同步和远程推送纳入 MVP，导致首个可用版本同时依赖认证、后端、冲突处理和推送基础设施。个人日用场景首先需要的是单台设备上可离线使用、可提醒、可自行备份的稳定闭环。

## 决策

- V1 Android 优先；iOS 保留跨平台代码兼容性，但不阻塞 Android 首发。
- V1 是单用户应用，不提供注册、登录、会话、账号资料或账号删除流程。
- SQLite 是 V1 业务数据的唯一事实来源。创建、编辑、完成、恢复和删除均先在本地事务中完成，界面不依赖网络反馈。
- V1 只使用设备本地通知，不注册推送 Token，不运行服务端通知 worker，也不依赖网络兜底。
- V1 提供用户主动触发的版本化 JSON 导出与导入：
  - 导出包含恢复事项、分类、提醒规则和本地设置所需的数据，不包含原生通知 ID、缓存、日志等可重建或临时数据。
  - 导入前校验格式版本和全部业务约束；确认后在单个事务中恢复，失败时回滚，不留下半导入状态。
  - 导入成功后重新建立本地通知计划；文件保存位置和传输方式由用户通过系统文件能力决定。
- 账号体系、Supabase 云同步、Outbox、Realtime、多设备冲突处理和远程推送延期到 V1 之后。
- 保留仓库中的 `supabase/` 配置、迁移和 RLS 测试骨架，不删除、不让其进入 V1 运行链路，也不以本地 Supabase 可用作为 V1 验收条件。

## 后果

- V1 可在无网络和无后端环境下完成核心闭环，开发与隐私边界更清晰。
- 卸载应用、设备损坏或未主动导出备份可能造成数据丢失；产品必须明确提示用户定期备份，不能把 JSON 导出描述成自动云备份。
- JSON 备份文件可能包含私密事项正文。应用不上传、分析或记录备份内容，分享和保管风险由界面明确说明。
- SQLite Schema 和 Repository 应保留稳定 UUID、时间戳及迁移能力，降低未来接入账号和同步时的数据迁移成本，但不得提前引入 V1 不需要的联网复杂度。
- 后续启用 Supabase 必须另立 ADR，说明本地数据认领、用户隔离、冲突语义、加密与迁移方案。
