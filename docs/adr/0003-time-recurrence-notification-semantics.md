# ADR 0003：V1 时间、重复与通知语义

- 状态：已采纳
- 日期：2026-07-26

## 背景

日期、时区、重复展开和通知调度必须使用同一组语义，否则事项在编辑、夏令时、旅行或通知对账后可能错日、错时或重复提醒。V1 需要收窄规则，以可解释、可测试的行为优先。

## 决策

### 时间表示

- 全天事项保存本地日历日期 `YYYY-MM-DD`，不把当地午夜转换成 UTC 瞬间。
- 非全天事项保存实际瞬间，并保留用于创建和展示规则的 IANA 时区；内部不得使用格式化文本代替日期时间字段。
- 系统时区、时钟或夏令时规则变化后，应用在下次启动或回到前台时重新计算并对账未来本地通知。

### 重复规则

V1 只支持以下受控规则：

- 每日：每天发生，`frequency = daily`、`interval = 1`。
- 每周：每周在用户选择的一个或多个星期发生，`frequency = weekly`、`interval = 1`。
- 两类规则均永不结束，不支持 `until`、`count` 或其他结束条件。

V1 不支持每 N 天/周（N > 1）、每月、每年、自定义 RRULE、“本次及以后”或任意规则文本输入。界面和导入校验必须拒绝这些规则，而不是静默降级。

每个系列保存稳定的本地日期/时间与 IANA 时区锚点。系列创建后，锚点日期、墙上时间、时区、频率和每周星期集合均锁定：

- 完成某次实例只创建该实例的完成记录，不结束或移动系列。
- 编辑某次实例不得改变系列锚点。
- V1 若要改变上述锁定字段，应明确提示用户删除原系列并创建新系列；不得暗中重写未来实例，也不得改变历史实例键。
- 跨夏令时展开时保持锚点时区中的墙上时间，而不是使用固定 UTC 小时间隔。

### 提醒基准

- 每条提醒规则明确保存 `anchor = start | due`，同一事项可以只设置开始提醒、只设置截止提醒、同时设置两类提醒或不提醒。
- 每个事项最多 10 条提醒；唯一性按 `(anchor, offsetMinutes)` 判断，因此“开始前 10 分钟”和“截止前 10 分钟”可以同时存在，同一锚点的相同提前量不能重复。
- 定时事项的 `start` 规则从开始时间向前计算，`due` 规则从截止时间向前计算；缺少对应时间时不能保存该锚点规则。
- 全天事项只支持 `start`，以该事项保存时区中的开始日 09:00 为提醒基准。设备时区变化后，已有全天事项的提醒瞬间不移动。
- 无日期事项不能设置通知。已经过期的提醒不补发，规划结果会将其记为已跳过而非安排失败。
- SQLite v3 和 V1 JSON 备份迁移旧规则时保持旧行为：定时事项有截止时间则迁移为 `due`，否则迁移为 `start`；全天事项迁移为 `start`；旧默认模板迁移为 `due`。
- 每条逻辑提醒使用包含锚点、规则 ID、实例键和触发时刻的 `wakewake-v2` 稳定键；升级对账会取消旧 `wakewake-v1` 请求，重复对账不得产生重复系统通知。
- 事项完成、取消或删除后，对账撤销仍待触发的提醒；调度失败不能回滚已成功保存的 SQLite 事项数据，必须独立显示并允许重试。
- 事项创建、更新、完成、恢复或删除的 SQLite 写入成功后，调用方必须立即启动一次非抛错的原生通知对账尝试，并可与 UI query 刷新并行等待；planner 直接读取已提交的 SQLite，不应因等待界面 refetch 而延迟近未来提醒登记。对账失败只能更新通知诊断，不能把已经提交的事项显示为保存失败。

### 常用模板

- 常用模板是仅用于新建定时事项的本地创建辅助，保存名称、默认时长和 0–10 条双锚点提醒规则；用户可以在设置中新增、编辑、删除和排序。
- 应用模板时保留当前事项标题、日期和开始时间，按模板时长重新计算截止时间，并用新 UUID 复制提醒。事项只保存具体时间与提醒，不保存模板引用；之后修改或删除模板不得影响已有事项。
- 模板与事项、设置一起保存在 SQLite 并纳入 JSON 备份；旧版本备份缺少模板时由导入规范化层补入当前默认示例。

### Android 调度边界

- V1 使用 `expo-notifications` 调度本地通知，不使用远程推送兜底。
- Android 13+ 在用户理解用途并主动开启提醒后请求通知权限；拒绝后核心事项功能仍可用。
- V1 不声明、不申请 `SCHEDULE_EXACT_ALARM` 或 `USE_EXACT_ALARM`，不引导用户开启精确闹钟特殊权限。
- 通知按操作系统允许的非精确机制尽力送达。系统省电、Doze、权限和厂商策略可能造成延迟，产品文案与验收不得承诺绝对准时。
- 已完成原生注册的本地提醒不依赖 JavaScript 进程持续运行，标准 Android 的普通进程死亡或从最近任务划掉应用后原则上仍可触发；无论启动时 AppState 初值如何，首次实际进入 active 都会强制重新注册未来有效请求，修复原生 alarm 丢失而 Expo 持久请求仍存在的状态。vivo 等厂商若在应用未运行时主动删除 alarm 或抑制 receiver，应用自身无法在该时刻重新登记。
- Expo 返回的持久请求仅表示请求已登记，不能单独证明 Android `AlarmManager` 仍有 live alarm；设置中的手动“提醒同步”因此执行强制重新登记。强制重建失败时必须清理失真的请求映射，使下一次修复能重新登记，不能显示为健康。
- 全局通知权限与 Android `reminders-v1` 通知类别分别诊断；类别被用户关闭时不得创建新类别绕过选择。界面中的“未来有效”是 planner 结果，“本次登记”是 Expo 接受的请求，二者均不承诺系统一定准时投递。
- Android 系统设置中的“强行停止”会将包置于 stopped state，应用、receiver 和云推送都不能可靠绕过。用户重新打开 WakeWake 后才能修复未来提醒；vivo 等厂商的自启动、后台活动和电池策略仍需真机验证。

## 后果

- 重复编辑器和测试矩阵显著收窄，客户端、备份导入和未来后端可以共享明确的校验规则。
- 用户不能直接调整现有系列的时间或规则，需要重建系列；界面必须在执行前说明历史完成记录与新系列的关系。
- 全天提醒在旅行或设备时区变化后仍表示“事项保存时区当天上午 09:00”；这与重复系列保持创建时墙上时间的规则一致，也避免旅行时已有提醒发生隐式移动。
- 由于不申请精确闹钟权限，通知允许出现操作系统造成的延迟；测试重点是规则正确、可撤销、可对账且不重复，而不是毫秒级准点。
